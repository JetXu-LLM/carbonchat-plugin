name: setup-carbonchat
description: Continue an explicitly requested CarbonChat setup after installation, or resume it safely when CarbonChat is already installed.
---

Preserve the user's install-and-open request. Follow the [installation flow](../../INSTALLER.md). Its public entry is https://carbonchat.codexforwork.com/install.md. If the user asked only to install, ask once whether to open The Lobby.

1. Reuse the successful installation result or known current-host status. Check unknown status once through a supported read-only action. Missing tools do not prove absence. Use this host's supported install/enable action only for an established missing/disabled state. Another client's CLI result, marketplace-add or a browser page is not current-host installation. On a blocker, give the actual state and one supported next action; stop.
2. A fresh installation needs no update check. For an already-installed fresh request, let `open-carbonchat-community` own the bounded version check and open attempt. Reuse established results. Setup, new-chat and authentication continuations do not check, install or update again.
3. After installation in this request, or for “Continue CarbonChat setup”, this skill owns one open attempt. Use the actual CarbonChat opener with its declared parameters; the published Thread opener is `open_carbonchat_thread` with `{}`. If the host offers tool discovery, use it once to load CarbonChat before declaring the opener absent. If absent, authorized UI access and an observed real CarbonChat entry permit one normal click. Do not replace it with a browser URL, guessed entrypoint or staging tool. Stop on actual denial or UI safety rejection.
4. If this host requires a new chat to load the known installed plugin, offer one continuation: start one new Codex chat, select CarbonChat with `@`, and send “Continue CarbonChat setup. It is already installed; open The Lobby.” / “继续完成 CarbonChat 设置：插件已安装，请打开大厅。” The user presses Send. Never send into a running task. In that continuation, skip installation and repeated investigation. If the opener or supported UI entry is still absent, report the host blocker and stop. Do not offer another new chat.
5. Guest reading needs no sign-in. Reuse a working connection. If the host explicitly requires connection, use its normal flow and let the user complete it. If The Lobby requests a connection but no authorization window appears, use Plugins → MCPs → CarbonChat → Authenticate when that control is available. This is the existing host-managed OAuth connection. The user completes GitHub and reviews access, then returns to The Lobby and chooses Continue after connecting. An authorization URL or enabled plugin does not prove connection success. After confirmed success, retry the pending open once. Stop on cancellation, refusal, failure or unclear state; do not restart login cycles. Never handle credentials, MFA or callbacks, or accept permissions, policies, age or profile choices for the user.
6. Keep installed, tool available, open accepted and room visible separate. Claim “The Lobby is open in Codex” only with visible MCP App evidence. If inspection is unavailable, say the open request was accepted and visibility is unverified. A browser read-only Lobby is a distinct fallback, not completion. Reply briefly with the observed result or one actual next action. Do not add model recommendations.

Opening authorizes no post, reaction, draft, publication or transfer of room content into the Agent chat. Browser use can read instructions, show required authentication or provide an explicitly chosen read-only fallback. Posting requires the user's GitHub sign-in, current policy/18+ review, nickname and service admission/account checks.
